# 基礎 18 · 四萬顆細胞的節奏：HCA 骨髓與 reference 註解

**難度**：★★ ｜ **預估時間**：1–1.5 個工作天 ｜ **對應集數**：B10、B11 ｜ **前置**：先完成基礎05（本題要用你的 bmcite 物件當 reference）；建議做過基礎08（大資料讀入的記憶體意識）

## 背景與研究主題

40,000 顆細胞（Human Cell Atlas ICA 骨髓，10x v2）在今天不算大資料，但它剛好卡在一個尷尬的位置：每一步都跑得動，可是每一步都要等——PCA 幾分鐘、UMAP 幾分鐘、一次 resolution 掃描半小時。這一題教的第一件事不是新方法，是**工作節奏**：哪些步驟該存 RDS 檢查點、參數嘗試該在多大的 downsample 子集上做、什麼時候才值得回全量重跑。做研究的人跟初學者的差別，常常就在這種「不浪費自己時間」的手感。第二件事是註解策略的升級：骨髓你在基礎05 已經用 CITE-seq 註解過一輪，這次拿你自己的 bmcite 物件當 reference 做 label transfer（基礎09 學過的招式，換一個大一個量級的 query），看「用自己做過的資料當 reference」能把 4 萬顆細胞的註解成本壓到多低、以及哪裡不能省。你的研究主題：

1. 中大型資料的分析節奏怎麼安排？downsample 試出來的參數，回到全量還可信嗎？
2. HCA 骨髓 40k 有哪些族群？多位捐贈者的批次效應需要整合嗎？
3. 用 bmcite 當 reference 做 label transfer，哪些型別轉移得漂亮、哪些 score 偏低？為什麼？

## 資料集

- **SeuratData `hcabm40k`**：40,000 cells，HCA ICA 骨髓，10x v2。
- 下載：R 內 `install.packages("SeuratData", repos="https://seurat.nygenome.org")` 後 `InstallData("hcabm40k")`、`LoadData("hcabm40k")`。
- 格式注意：捐贈者等欄位在 metadata，欄名與捐贈者數以 `colnames(obj[[]])`、`table()` 實際確認為準。本題建議 16 GB RAM；bmcite reference（~30,672 cells）與 query 同時在記憶體裡，開工前把不相干的大物件清掉。

## 任務

### 階段 A：節奏設計與標準流程（對應 B10）

1. 載入後先偵查：`dim()`、metadata 欄位、捐贈者分布。設計你的**檢查點策略**：決定在哪幾步之後 `saveRDS()`（建議至少：QC 後、PCA 後、最終物件），檔名帶版本或日期。每個主要步驟用 `system.time()` 記錄耗時，做成一張小表——這張表就是你的節奏依據。
2. Downsample 試參數：隨機抽 5,000 顆細胞建一個試驗子集，在上面快速掃 nPC 與 resolution（參數三件事照規矩），選出候選參數再回全量跑。記錄：全量結果與子集結果在「族群層級」一致嗎？哪些群是子集裡看不見、全量才浮出來的？
3. QC 三件事照舊（10x v2 的深度比 v3 淺，分布長相自己看，別套別題的閾值），跑標準流程到 UMAP＋分群。

### 階段 B：批次決策與自己的註解（對應 B10、B11）

4. 按捐贈者上色 UMAP，評估批次效應：捐贈者效應有大到需要整合嗎？做一個明確決策（整合／不整合，用什麼方法、什麼範圍）並記錄理由——這是 B11 的整合範圍判斷在「同技術、多捐贈者」情境的版本。
5. 用你在基礎05 練熟的骨髓 marker（T/B/NK、單核球、紅系、前驅細胞 CD34 等；自查補齊）快速做一版自己的註解——這版是階段 C 對質用的基線，粒度到大類即可。

### 階段 C：label transfer 與信任邊界（對應 B11）

6. 載入你基礎05 完成的 bmcite 物件（含你的最終 WNN 註解欄）。確認兩邊 normalization 一致後 `FindTransferAnchors`＋`TransferData`（基礎09 的骨架；4 萬顆 query 的記憶體與提速手段見提示 3），把 `predicted.id` 與 prediction score 掛回 metadata。
7. 檢視品質：score 分布、score 低的細胞在 UMAP 的位置、逐型別平均 score 表。交叉表：你的註解 × `predicted.id`，分歧群逐一裁決（你錯／轉移錯／reference 沒有這型別／粒度不同——基礎09 的 (a)–(d) 分類照用）。想一件事：bmcite 的註解有 ADT 蛋白證據撐腰，hcabm40k 只有 RNA——哪些「蛋白才分得開」的亞群（基礎05 找到的那些）注定轉移得勉強？
8. 寫 200–300 字節奏＋註解總結：這題你實際花了多少機器時間 vs 人的時間？downsample 幫你省了什麼、騙過你什麼？label transfer 讓你少查了多少 marker、但哪些群你仍然回頭補了人工證據？

## 繳交物

1. 可重跑的 R 專案（含檢查點 RDS 的存讀邏輯與耗時紀錄表）。
2. 圖：QC 分布、捐贈者上色 UMAP、自己註解的 UMAP、`predicted.id` 上色 UMAP、score 分布與逐型別 score 圖（英文標籤）。
3. 分析筆記：參數三件事＋downsample vs 全量對照＋整合決策＋交叉表與逐群裁決。
4. 節奏＋註解總結（200–300 字）。

## 自我檢核點

- [ ] 有檢查點策略與耗時表，重跑任一階段不必從頭來過
- [ ] downsample 的角色說得清楚：它產出「候選參數」，定稿一律在全量上驗證
- [ ] 整合／不整合有明確決策、理由與圖為證，不是預設照做
- [ ] score 低的細胞有被追查（在哪、是誰、為什麼），且能連回「reference 靠 ADT 分的亞群」這條線
- [ ] 每個分歧群的裁決分得清 (a)–(d) 四種情況
- [ ] 總結有誠實的時間帳：機器時間、人的時間、省掉與省不掉的部分

## 提示（卡關再看）

<details><summary>提示 1：檢查點與記憶體</summary>
`saveRDS(obj, "checkpoints/01_postQC.rds")` 這類命名讓你隨時能從中途接手；改參數重跑時從最近的檢查點 `readRDS()`。大物件用完 `rm()`＋`gc()`；`lobstr::obj_size()` 隨手量，別等爆了才查。
</details>

<details><summary>提示 2：downsample 的正確姿勢</summary>
`subset(obj, cells = sample(Cells(obj), 5000))`（記得 set.seed 已在通用規範裡）。注意兩個陷阱：稀有族群在 5k 子集裡可能只剩幾顆、甚至消失，所以「群數」不能拿子集的當真；HVG 與 PCA 在子集上重算，選出的參數是初稿不是定稿。
</details>

<details><summary>提示 3：4 萬顆 query 的 transfer 提速</summary>
`FindTransferAnchors` 吃時間的是 anchor 搜尋：dims 給 1:30 起步、必要時 `reduction = "pcaproject"`（預設）勿改成更貴的選項；記憶體吃緊可分批 transfer（把 query 按捐贈者拆開各自 transfer 再合併，順便看轉移品質有沒有捐贈者差異）。`prediction.score.max` 之外，逐型別攤開 `prediction.score.*` 各欄看騎牆細胞。
</details>

## 進階挑戰

- 用 `MapQuery()` 把 40k 細胞投影到 bmcite 的 UMAP 座標上（reference mapping 的完整版），與你自己的 UMAP 並排。
- 把 downsample 規模掃 2k/5k/10k，量化「參數結論穩定下來」需要多少細胞——為你以後更大的資料建立自己的經驗法則。
- 正常骨髓階層的知識在進階05（AML 的惡性像正常）是主戰場；reference 級的大型 CITE-seq 參考集見進階58（Azimuth PBMC）；圖譜級 mapping 的終點站是進階30。
